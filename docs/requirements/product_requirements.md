# InnoSkill 产品需求规格（草案）

## 1. 依据与状态

- 唯一需求依据：[问题定义](problem_definition.md)，本文将其转化为可评审、可追踪的需求。
- 产品面向中小学教师与职前教师，核心是让教学经验可读、可执行、可分享、可改进。
- 本文描述目标能力，不代表已实现，也不代表全部纳入首次交付。
- 预计交付目标为 **2026-12-31**；首期范围、质量门槛与公开发布日期待确认。
- 下列验收条件用于需求讨论与后续测试设计；依赖未决规则的条件暂不能签署通过。
- 创作者、使用者、学习者、衍生创作者是参与角色，同一账号可以兼具多种角色。

## 2. 范围与优先级管理

- 目标范围包括创作、发现、阅读、运行、社区协作和商业机制。
- 初始分类为备课、出题、PBL 设计，分类和 Tag 应可扩展。
- 不将产品限定为教学材料生成器；学习教学方法与执行 Skill 同样重要。
- 不承诺任意上传文件可执行，不承诺所有外部工具具有一致体验。
- 首期候选闭环：创作 → 发布 → 发现 → 阅读 → 平台运行 → Issue 反馈。
- 候选闭环只是建议；收费、Fork、外部接入等能力的首期取舍必须单独批准。
- 每项需求需记录首期纳入状态、负责人、依赖、验收证据；未批准时统一为“待定”。

## 3. 需求、用户故事与验收条件

下表中的条件以批准后的 Skill 规范、授权及计费规则为前提，不隐含这些规则已确定。

| 需求 ID | 用户故事 / 目标能力 | 验收条件 |
| --- | --- | --- |
| PR-01 | 作为创作者，我希望用模板表达教学经验 | 可填写方法、步骤、关键判断与约束；保存后重新读取不丢失内容；必填项按确认后的规范校验 |
| PR-02 | 作为创作者，我希望可视化编辑 Skill | 编辑结果与文字化内容语义一致；保存及错误提示可理解；不把未保存内容显示为已发布 |
| PR-03 | 作为创作者，我希望 AI 辅助生成和修改 | 建议与原文可区分；创作者确认后才写入；失败可恢复，不能自动替创作者发布 |
| PR-04 | 作为创作者，我希望上传已有 Skill | 合规样例可导入；不支持格式、超限或危险内容给出明确提示；上传不自动授予运行权限 |
| PR-05 | 作为创作者，我希望发布并维护 Skill | 发布记录作者、内容版本、分类、Tag 与授权信息；他人不能修改我的项目；更新可追溯 |
| PR-06 | 作为使用者，我希望按分类与 Tag 发现资源 | 初始三类可浏览；新增分类无需改变产品定位；筛选结果不泄露无权访问的内容 |
| PR-07 | 作为学习者，我希望阅读教学方法而非仅看结果 | 在授权范围内可读步骤与约束；学习者能解释关键判断，并在新教学情境中尝试应用 |
| PR-08 | 作为使用者，我希望在平台 AI 中运行 Skill | 使用明确版本与输入；运行前展示适用权限和费用提示；成功、失败、取消等状态可追踪 |
| PR-09 | 作为使用者，我希望接入外部 AI 工具 | 对每个批准支持的工具提供接入说明与版本边界；代表性样例验证通过；不支持情况明确告知 |
| PR-10 | 作为社区参与者，我希望用 Star 表达认可 | 可添加及撤销；重复操作不重复计数；未授权操作被拒绝 |
| PR-11 | 作为使用者，我希望通过 Issue 提交问题 | 可关联 Skill 并提交反馈；作者能查看和回应；内容可见性与操作权限遵循批准规则 |
| PR-12 | 作为衍生创作者，我希望在授权允许时 Fork | 校验衍生许可；记录来源及来源版本；不允许的 Fork 被拒绝；免费不自动意味着可衍生 |
| PR-13 | 作为创作者，我希望自主选择免费或收费 | 价格状态清楚；免费 Skill 不收交易抽成；收费价格变更权限受控；购买授权按批准规则生效 |
| PR-14 | 作为交易参与者，我希望理解抽成与结算 | 收费交易列出金额与抽成依据；支付回调不重复入账；交易、退款和结算记录可核对 |
| PR-15 | 作为平台 AI 使用者，我希望 Token 费用透明 | 免费 Skill 仍提示可能产生 Token 费用；计量、价格版本、费用可核对；重试不重复扣费 |
| PR-16 | 作为上下游创作者，我希望衍生收益可追溯 | 单层付费衍生标价为 a+b；分别记录上游 a 与新增 b 的收益归属；抽成与净收入另列 |
| PR-17 | 作为参与者，我希望内容与数据受保护 | 无权用户不能读取、下载或执行受限内容；敏感数据与密钥不进入公开内容或普通日志 |
| PR-18 | 作为平台运营方，我希望治理操作可审计 | 审核、下架、权限与财务关键变更留痕；操作范围受控；争议处理遵循批准流程 |

## 4. 代表性验收场景

1. 教师整理真实教学经验，以批准的创作方式形成可读 Skill 并发布。
2. 另一教师通过分类或 Tag 找到资源，阅读方法并解释其适用边界。
3. 在权限与费用明确后运行指定版本，检查输出是否符合教学约束。
4. 使用者提交有效 Issue，创作者回应并形成可追溯的改进。
5. 若交付包含 Fork，验证许可、来源版本与衍生作品关系。
6. 若交付包含收费，核对标价、授权、Token 费用、收益归属及异常交易。
7. 若交付包含外部接入，逐工具、逐支持版本验收，不用单一成功案例代表全部兼容。

## 6. 质量与价值验证

- 教学价值：观察方法表达完整性、学习者理解和迁移能力、输出修改负担。
- 易用性：记录首次创作完成率、耗时、所需协助和首次运行成功率。
- 社区价值：记录有效 Issue、回应及有实质改进的 Fork，不以数量独立证明成功。
- 商业价值：验证价格理解度、交易准确性和规则接受度，不预设收入承诺。
- 安全与可靠性：权限隔离、失败恢复、财务幂等、数据保护必须纳入验收。
- 指标数值、样本规模、性能与可用性目标需调研后批准，不在本文虚构。
