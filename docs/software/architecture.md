# InnoSkill 逻辑架构草案

## 1. 定位与约束

- 依据：[问题定义](../requirements/problem_definition.md)与[产品需求](../requirements/product_requirements.md)。
- 本文是逻辑设计建议，不代表已有服务、数据库、接口或部署设施。
- 不指定编程语言、框架、数据库、云厂商、支付渠道或模型供应商。
- 逻辑模块不等于独立服务；首期可如何组织代码，需在范围明确后决策。
- 目标是同时支持经验阅读与执行，并对授权、版本和费用建立明确边界。
- 全部目标能力不等于首期承诺；实现顺序见[路线图](../mgmt/roadmap.md)。

## 2. 逻辑分层

```text
教师 / 职前教师 / 运营人员
            ↓
用户交互层：创作、发现、阅读、运行、反馈、交易与运营
            ↓
应用用例层：发布、获取授权、执行、Fork、购买、结算
            ↓
领域层：Skill、社区、授权、运行、交易、收益与治理
            ↓
端口与适配层：存储、平台 AI、外部工具、支付、计量
```

- 交互层不决定权限或收益公式，最终校验应位于可信应用边界内。
- 应用层协调流程与失败处理；领域层维护规则，适配层处理外部差异。
- 外部结果视为不可信输入，不因支付回调或模型响应而跳过校验。
- 跨领域流程需定义一致性、重试与补偿策略，不能假定所有动作同时成功。

## 4. 领域实体建议

| 实体 | 关键概念与约束 |
| --- | --- |
| 用户主体 | 创作者等角色可重叠；运营权限单独授权，不能因创作者身份获得 |
| Skill 项目 | 标识、作者、分类、Tag、发布状态；承载可持续维护的资源 |
| Skill 版本 | 内容、格式、依赖、方法、步骤与约束；运行与衍生应定位到明确版本 |
| 分类与 Tag | 初始分类不限制扩展；变更不应破坏已有资源引用 |
| 许可 / 访问授权 | 分开描述阅读、运行、导出、Fork、再销售权限；免费不等于无限许可 |
| Star / Issue | 关联主体及项目；反馈可见性、维护权限与删除政策待确认 |
| 衍生关系 | 来源项目、来源版本、许可依据；多来源和多层链规则待确认 |
| 运行记录 | 输入引用、Skill 版本、执行环境、状态、用量及失败信息 |
| 价格规则 / 快照 | 标价与规则版本；交易历史不能随当前价格修改而改变 |
| 订单 / 支付记录 | 交易状态、金额、支付关联、幂等标识；不把发起支付视为成功 |
| Token 用量记录 | 计量来源、执行关联、价格版本与计费结果；避免重复计量 |
| 收益分配 / 结算记录 | 上下游归属、抽成、退款与实收区分；保留对账关联 |
| 治理 / 审计记录 | 审核、下架、授权变更和账务操作；敏感内容不直接写入审计正文 |

实体与字段是建模建议，尚不是已批准的数据表或接口契约。

## 5. 领域边界与关键流程

- Skill 边界负责内容校验和发布版本，不自行处理付款或推断衍生许可。
- 授权边界统一判断阅读、编辑、运行、导出、Fork 和运营动作。
- 社区边界负责反馈与协作关系，不因 Star 或 Issue 授予内容访问权。
- 运行边界先校验版本、授权、依赖与执行权限，再调用模型适配端口。
- 商业边界维护订单、价格快照和收益依据；Token 费用与 Skill 价格分别记录。
- 治理边界决定审核和下架动作；如何影响既有授权需先确认业务规则。
- 发布流程：校验内容与许可 → 建立版本 → 发布可见信息；失败不得留下虚假发布状态。
- 购买流程：形成价格快照 → 支付确认 → 赋予约定授权 → 记录收益；各步需支持核对。
- 运行流程：鉴权 → 费用提示 → 执行 → 获取可信计量 → 按规则计费；失败费用待决。
- Fork 流程：校验许可 → 固定来源版本 → 建立衍生关系 → 独立编辑；不静默复制授权。
- 单层衍生采用 a+b 标价和分项归属；抽成扣除位置未确定前，不推导净收益。
- 多层、多来源、改价、退款等流程在规则批准前不可按单层公式直接推广。

## 6. 外部适配设计

| 适配边界 | 要求 |
| --- | --- |
| 平台 AI | InnoSpark 等是候选环境；明确请求、响应、取消、超时、用量与错误契约 |
| 外部工具 | WorkBuddy、Codex、Claude Code、pi-coding-agent、dsh、zcode 仅是接入目标 |
| Skill 导入 / 导出 | 按格式及版本校验；声明能力损失，不承诺任意格式等价转换 |
| 支付与结算 | 渠道待选；验证回调来源、重放保护、对账与退款能力 |
| 持久化与文件存储 | 技术待选；保障版本引用、权限隔离、恢复与敏感数据生命周期 |

- 对每个外部工具维护支持版本、格式、安装方式、限制和验证证据。
- 接入方式可能是导出、安装说明或接口调用，不能假定所有工具有统一 API。
- 不调用未经确认的服务；配置与密钥管理不得绑定到 Skill 文本。

## 7. 安全与非功能边界

- 上传视为不可信：限制类型与大小，校验路径和依赖，禁止任意文件写入。
- Skill 指令和模型输出不得提升系统权限；工具调用需明确授权和资源限制。
- 网络、文件、密钥访问采用最小权限；具体隔离方案在技术选型时验证。
- 阅读、搜索、预览、下载、外部导出均须经过内容权限检查，防止付费内容旁路泄露。
- 教师和学生数据遵循最小收集原则；真实敏感数据不作为默认测试样本。
- 凭据、个人信息及完整运行输入不应直接进入普通日志；保留期限待批准。
- 财务关键操作需幂等、审计及可对账，失败补偿不能掩盖金额差异。
- 性能、容量、可用性、恢复目标尚未确定，须结合首期场景制定再验证。

## 8. 后续决策与验证

- 先确认 Skill 规范、授权模型、首期范围和收费规则，再比较技术方案。
- 技术决策需记录候选项、验证样例、取舍、成本与可回退路径。
- 按[测试策略](testing_strategy.md)验证权限、商业收益、外部兼容及教学价值。
- 任何新增架构假设都应回溯需求，不把待决业务规则隐藏在实现细节中。
